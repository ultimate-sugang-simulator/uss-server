## 대상

- 엔드포인트: `GET /api/v1/carts`
- 실행 경로: `CartController.getCartedCourse` → `CartService.getCartedCourse` → `CartRepository.findByMemberId`, `CartRepository.countCartedCoursesByCourseId`
- 인증: `@Auth` 있음 → 회원 시드 필요
- 예상 쿼리 목록 (요청 1회 기준)
  1. `CartRepository.findByMemberId` - `carts`를 `member_id`로 필터, `courses`를 inner join fetch, `course_schedules`를 left join fetch, `created_at` 정렬. 장바구니, 강의, 시간표를 한 쿼리로 읽는다 (강의, 시간표 배치 쿼리는 나가지 않는다)
  2. `CartRepository.countCartedCoursesByCourseId` - `carts`를 `course_id IN (...)`으로 필터해 `course_id`별 COUNT. 장바구니가 비어 있으면 실행되지 않는다 (빈 장바구니는 1쿼리, 아니면 2쿼리)
  3. 지연 로딩 후보 없음 - `Course.department`는 `@Enumerated` 컬럼이라 조인이 없고, `Cart.member`는 조회 경로에서 접근하지 않는다

### 진단

- 병목 성격: 이 데이터 규모에서 DB 쿼리 병목 없음. 응답시간을 지배한 커넥션 풀 대기는 VU 30 > 풀 10인 부하 조건이 만든 것으로, 대상 API의 결함으로 보지 않는다. 사이클 없이 종료한다.
- 근거: 요청당 SQL 2건, 각 1ms 미만, DB 실행 시간 합 1.78ms (요청당). p95 57.0ms / p99 88.2ms / 705 RPS, 에러 0. 재측정(같은 조건)에서 요청 84,537건, p95 57.7ms, p99 90.0ms로 재현. 부하 유지 구간의 CPU 샘플(8코어): 호스트 약 88% 사용(sys 약 31%), JVM 코어 1.1~1.6개, MySQL 컨테이너 코어 1.6~1.9개, HikariCP active 10/10, pending 19~20 상시. 커넥션 점유 시간 = 10 / 705 RPS = 14.2ms, 응답시간 = (20 / 10 + 1) × 14.2 = 42.6ms로 VU당 실측 42.5ms와 일치.
- 예상 쿼리 목록과 어긋난 지점: 없음. 지연 로딩 쿼리 없음.
- 판정에 반영하지 않은 위험 신호: (1) 요청당 왕복 7번 중 5번이 트랜잭션 제어문이고, 커넥션 점유 14.2ms 중 12.4ms가 쿼리 실행이 아닌 왕복에 쓰인다(왕복당 약 1.8ms - macOS Docker Desktop 포트 포워딩과 호스트 CPU 포화가 단가를 키운 환경 요인. 왕복 횟수 자체는 환경과 무관). (2) 쿼리 1의 읽은 행/반환 행 205 - 읽는 행 수가 담긴 강의의 담기 수(인기도)에 정비례해 규모 성장 시 커지는 구조.
