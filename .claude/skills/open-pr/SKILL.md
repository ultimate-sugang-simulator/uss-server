# PR 생성

대상 브랜치: $ARGUMENTS (비어있으면 dev)

## Phase 1: 현재 브랜치 및 변경 사항 파악

1. `git branch --show-current`로 현재 브랜치명을 확인하라
2. 브랜치명에서 이슈 번호를 추출하라 (형식: `{type}/{이슈번호}-{설명}`)
   - 예: `feat/123-course-search` → 이슈 번호 `123`
   - 이슈 번호가 없으면 사용자에게 물어보라
3. `git log dev..HEAD --oneline` (또는 $ARGUMENTS..HEAD)으로 이 브랜치의 커밋 목록을 확인하라
4. `git diff dev...HEAD --stat`으로 변경된 파일 목록을 파악하라

> 다음 Phase 조건: 이슈 번호와 변경 사항이 파악되었을 때

> Skip 조건: 없음 (필수 Phase)

## Phase 2: PR 제목 및 본문 작성

**이 PR 본문은 이력서와 경험 기술서의 소스로 쓰인다.**
Problem과 Solution만 읽어도 "무엇이 왜 문제였고, 어떤 방법을 왜 골랐는지"가 서술로 남게 써라.

1. `.github/PULL_REQUEST_TEMPLATE.md`를 Read로 읽어 섹션 구조(`PR Summary`, `Problem`, `Solution`, `Related Issue`)를 그대로 따르라.
   - 템플릿의 HTML 주석(`<!-- ... -->`)은 작성 가이드다. 본문에 포함하지 마라.
   - 섹션 제목은 `##`, 섹션 사이의 `<br>`은 렌더링 장식이다. 지우거나 바꾸지 말고 그대로 유지하라.
2. `.claude/spec/git-convention.md`를 Read로 읽어 커밋 메시지 형식, 제목 규칙, 표기 규칙을 확인하라.
3. PR 제목은 `{type}: {설명}(#{이슈번호})` 형식으로, git-convention.md의 제목 규칙을 따른다.
   - (지양) `refactor: 장바구니/수강신청 검증 로직 분리 및 중복 제거(CartService/RegistrationService)`
   - (지향) `refactor: 담기와 신청의 검증 로직 중복 제거(#123)`
4. 문체
   - 본문 서술은 존댓말(`~합니다`, `~했습니다`)
   - 소제목은 명사형으로 끊어라 (예: `**해결 2 - 시간표 충돌 판정 공통화**`)
   - 표기 규칙(가운데점 대신 콤마, 긴 대시 대신 짧은 대시)을 지켜라
   - 용어는 현업에서 통용되는 쪽을 골라라. (`전체 스캔` 대신 `풀스캔`, `검사 행` 대신 `스캔 행`, `술어` 대신 `WHERE 조건`)
   - **영어를 한국어로 옮긴 조어를 쓰지 마라.** 기준은 "한국 개발자가 동료에게 말로 설명할 때 쓰는 단어"다.
     영어가 더 흔한 용어는 영어 그대로 쓰고(fetch join, filesort, projection, cache-aside, warm-up, TTL, fail-open, stampede, hit / miss),
     그 밖은 사전 번역이 아니라 뜻이 통하는 한국어로 풀어 써라. 번역투가 보이면 문장을 다시 써라.

     | 지양 | 지향 |
     |---|---|
     | 물질화된 읽기 모델 | 미리 만들어 둔 읽기용 데이터 (또는 그냥 read model) |
     | 사전 적재, 예열 | warm-up |
     | 조인 페치 | fetch join |
     | 지연 초기화 예외 | `LazyInitializationException` |
     | 쓰기 관통 캐시 | write-through |
     | 실패 개방 | fail-open |
5. 블록 구분
   - `<br>`은 섹션(`##`) 사이뿐 아니라 **굵은 소제목 블록 사이마다** 넣어라.
     문제 1과 문제 2 사이, 해결 2와 해결 3 사이, 표와 다음 소제목 사이가 모두 해당한다.
   - 표에 이름을 붙일 때는 굵게 처리하고 그 앞뒤에도 `<br>`을 넣어라. (예: `**학과별 강의 수**`)
   - 소제목 하나가 문단과 표를 여러 개 거느리면 그 안에서는 `<br>`을 넣지 마라. 블록의 경계에서만 쓴다.
6. 섹션별 작성 규칙
   - **PR Summary**: 변경 사항을 1~2문장으로. 여기서 전체 그림이 잡히게 하라
   - **Problem**: 문제 상황과 원인. 그래서 무엇이 잘못되고 있었는지(영향)를 반드시 드러내라
   - **Solution**: 채택한 방법과 그것을 고른 이유. 접근의 핵심이 되는 클래스나 설정명만 필요할 때 언급하라
   - **Related Issue**: `- close #{이슈번호}`
7. 문제가 여러 개면 번호로 분기하고, Problem과 Solution의 번호를 1:1로 맞춰라.
   문제가 하나면 번호를 붙이지 말고 문단으로만 써라.

   ```
   ## Problem
   **문제 1 - 담기와 신청의 검증 로직 중복**
   ...
   **문제 2 - 정원 검사와 증가 사이의 경합**
   ...

   ## Solution
   **해결 1 - 시간표 충돌 판정을 CourseValidator로 통합**
   ...
   **해결 2 - 정원 증가를 조건부 UPDATE로 변경**
   ...
   ```

8. 설계 결정이 여러 개인 해결(캐싱, 락, 인덱스처럼 선택지가 있었던 기법)은 **결정을 나열하지 말고 이어지게 써라.**
   순서는 "왜 이 기법인가 → 무엇을 대상으로 → 어떻게 (키, 갱신, 실패 시) → 그래서 무엇을 하지 않았나"이고,
   앞 결정이 뒤 결정의 전제가 되어야 한다. 근거는 기록 문서(`record.md`의 도입 근거, 설계 결정, 검토했지만 택하지 않은 안, 계획서)에서 가져온다.
   - 기법에 통용되는 이름이 있으면 그 이름을 써라 (cache-aside, write-through, refresh-ahead, single-flight, fetch join, projection).
     이름이 없으면 한 문장으로 풀어 쓰고 억지로 이름을 붙이지 마라.
   - 깊이는 **그 기법 자체의 선택**까지다. 무엇을 캐시하고 무엇을 라이브로 두는지, 키는 무엇이고 왜인지, 언제 갱신하고 실패하면 어떻게 되는지까지 쓴다.
     주변 장치(예외 핸들러 구조, 설정 클래스 배치, 어노테이션 선택)는 한 문장 이하로 줄이거나 생략한다.
   - 검토했다가 버린 안은 "무엇을 왜 버렸는지"를 관측된 사실 한 줄로 남겨라. 버린 이유가 없는 대안은 적지 마라.
   - 서비스 특성에서 출발한 근거(트래픽 모양, 데이터가 바뀌는 때, 정합성 요구)를 기법보다 앞에 둬라.
     "빠르니까", "많이 쓰니까" 같은 일반론만으로 기법을 정당화하지 마라.

9. 개선이 여러 단계로 쌓인 PR(측정 사이클, 단계별 리팩토링)은 **앞 단계가 드러낸 문제를 뒤 단계가 받는 순서**로 Problem과 Solution을 배치하라.
   각 문제에는 "그 시점에 그것이 왜 최대 비용이었는지"를 앞 단계의 결과로 설명하고, 마지막에 단계별 추이를 한 줄로 붙여라
   (예: `p95가 4,217 → 2,619 → 2,187 → 766 ms로 움직였습니다`).

10. 금지 사항
   - 변경 파일과 메서드를 나열하지 마라. diff가 이미 보여준다
   - 각 문단은 2~4문장으로 유지하라. 내용이 없는데 분량을 채우지 마라 (작은 변경은 짧은 게 정상이다)
   - 커밋 메시지를 그대로 복사하지 마라. 변경을 이해한 뒤 문제와 해결의 언어로 다시 써라

### 성능 최적화 PR

Phase 1에서 파악한 변경이 성능 개선이면 위 규칙에 아래를 더해 쓴다.
**성능 PR의 값어치는 수치에 있다.** "빨라졌습니다"를 서술로만 쓰지 마라.

1. 수치는 `.claude/resources/perf/{이슈번호}/{슬러그}/record.md`의 **최종 요약**에서 가져온다.
   재지 않은 값을 추정해 채우지 마라. 측정하지 않은 항목은 그 사실을 적는다.
2. Before와 After가 있는 수치는 표로 제시하고 **변화** 칼럼을 붙인다.
   - 줄어드는 값은 퍼센트(`-99.2%`), 늘어나는 처리량은 배수(`19.3배`), 이미 퍼센트인 값은 퍼센트 포인트(`-77.3%p`)
   - 소제목 옆에 측정 기준을 괄호로 밝힌다. (예: `**전공 강의 조회 풀스캔** (강의 2만 건, 학과 20종 기준)`)
3. 쿼리 개선이면 표를 두 종류로 나눈다. 한 표에 섞지 마라.
   - **실행 계획 표**: 접근 방식, 사용 인덱스, 스캔 행, 반환 행, `Handler_read_rnd_next`, 실행시간
   - **부하 지표 표**: 쿼리 평균 실행시간, p95, p99, 처리량, 커넥션 풀 점유율
4. 대상 쿼리가 여러 개면 쿼리별로 표를 나누고 표 앞에 굵은 이름을 단다. 한 표에 몰아넣지 마라.
5. 인덱스를 추가했으면 인덱스 정의를 한 줄로 먼저 적고, **컬럼마다 그 자리에 둔 이유를 문단으로** 밝힌다.
   이 근거는 표로 만들지 마라. "왜 이 순서인가"가 서술로 이어져야 한다.
   등호 조건과 범위 조건의 순서, 정렬을 인덱스로 푼 근거를 반드시 포함한다.
6. 측정 조건(VU, duration, 데이터 규모)과 산출물 경로를 마지막 블록에 한 문단으로 밝힌다.
   로컬 측정이면 처리량과 응답시간이 하드웨어에 의존한다는 사실과, 개선 판정을 무엇으로 했는지를 함께 적는다.
7. 측정했지만 개선하지 않기로 한 대상도 그 사실과 근거 수치를 남긴다. 개선한 것만 골라 쓰지 마라.

## Phase 3: PR 생성

1. 대상 브랜치를 결정하라:
   - $ARGUMENTS가 있으면 해당 브랜치로
   - 없으면 `dev`로
2. 현재 브랜치가 원격에 push되어 있는지 `git status`로 확인하라
   - push되지 않았으면 사용자에게 알리고 중단하라
3. 본문은 스크래치 파일에 저장한 뒤 `--body-file`로 넘겨라 (긴 본문의 셸 이스케이프 사고를 막는다).
4. 다음 명령으로 PR을 생성하라:
   ```bash
   gh pr create --title "{제목}" --body-file {본문파일} --base {대상 브랜치} --assignee @me
   ```
   - 담당자는 항상 호출자 본인(`@me`)이다.
   - 리뷰어는 지정하지 않는다. 현재 이 저장소의 커밋 권한자는 한 명이라 지정할 대상이 없다.
     기여자가 늘면 `.claude/spec/git-convention.md`에 팀 로스터를 두고 여기서 참조하도록 바꾼다.
